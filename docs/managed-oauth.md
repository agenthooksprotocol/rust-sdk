# Host-managed OAuth

Enable `managed-oauth` to use `auth::managed::ManagedOAuth` with Tokio. The default SDK has no OAuth dependency. `ManagedOAuth` implements `AuthProvider`; custom providers remain supported. Use `AuthProviders` to select bearer, OAuth and unbound routes explicitly. An explicit `Authorization` header bypasses provider lookup and challenge handling.

## Supply network, policy and storage

The helper creates no browser, callback listener, HTTP client, worker or persistent store. Supply these host boundaries:

- `OAuthNetwork`: enforce destination policy against connection-time resolved addresses, pin approved addresses, verify TLS identity, disable redirects and bound streaming response reads to 1 MiB. A preliminary URL/DNS check alone does not prevent rebinding. `check` also approves authorization URLs before they are displayed. Never log OAuth requests or responses.
- `OAuthPolicy`: approve the exact issuer, resource, client, scopes and advertised authorization/token endpoints. A public HTTPS endpoint is not permission to disclose a client secret. Metadata and challenge scopes are untrusted requirements, not consent.
- `CredentialStore`: coordinate exclusive ownership and atomic versioned compare-and-swap across all processes sharing credentials. Use `SessionKey::as_str()` as the storage identity. Acquisition, reads and writes must be cancellation-safe and obey the operation budget. Dropping a guard must release ownership. A process-local mutex is sufficient only for a single-process host.

Records contain access/refresh tokens, the client they were issued to and, only with `.persist_pending_logins()`, pending logins with their PKCE verifier and state. Encrypt/protect them as credentials; do not log or send them on the AHP wire. Discovery runs outside credential-store ownership; token acquisition/refresh remains serialized per grant. Hosts must not introduce a second lock order around network or policy callbacks.

## Choose scope and consent boundaries

Configure `OAuthClientConfig::new(namespace, client_id, flow)` and call `.scopes(requested, allowed)`. Requested scopes are asked for in every acquisition but are never mandatory: a grant lacking them still satisfies an operation. A binding preset's optional `scopes` must equal them, else the operation fails `invalid_configuration`. Allowed scopes are the local ceiling, defaulting to the requested set; a requested scope outside it fails `invalid_configuration`. `.required_scopes(required)` sets host-required scopes, mandatory for every operation. The ceiling governs what the SDK requests and records; it does not constrain what an issued token can do. Hosts that need enforcement validate tokens in their own policy.

The SDK records granted scopes only. An acquisition (PKCE consent or client credentials, including step-up for an existing grant) requests the previously granted scopes plus the requested and required scopes within the caller's ceiling. It records the response scopes (the requested set when `scope` is omitted; an absent, `null` or blank `scope` counts as omitted, and any other non-string or a string that is not single-space-separated scope tokens fails `provider_failed`) intersected with the previous grant plus the acquiring ceiling; for PKCE that is the ceiling stored with the pending login. Earlier scopes are never lost. A refresh records the response scopes intersected with the previous grant, so it never broadens consent and is not narrowed by the current ceiling. At use, the effective scopes are the grant intersected with the current caller's ceiling. Scopes outside it, such as `openid` or `offline_access`, are ignored, never an error. An operation's required set is the host-required scopes, plus explicit `prepare_with_required` scopes, plus a validated 403 `insufficient_scope` challenge's scopes. A required scope outside the ceiling fails `access_denied` locally, before any network request, on every path (lookup, delivery, `prepare` and challenge handling). An acquired or refreshed grant whose effective scopes miss the required set fails `access_denied`; the grant, including any rotated refresh token, is still saved. Every scoped `access_denied` and `interaction_required` carries the full required set in `HookError::required_scopes()`, deduplicated and sorted. Errors raised by host callbacks (`OAuthPolicy`, `OAuthNetwork::check`) and non-scope refusals carry none.

Binding identity is namespace, backend, exact destination and event/upload purpose. Grant identity is namespace, exact issuer and resource, client identity, flow and grant partition. The client identity is the configured client source, as in MCP clients: `preregistered:<client_id>`, `cimd:<url>` or `dcr`; a client issued by dynamic registration never enters a key, so registering a new one does not move the grant. The ceiling, secrets, token-endpoint auth method, metadata capabilities and scope sets are not identity either, so changing them never orphans a grant. Use separate namespaces for host accounts or registrations.

Default grants are isolated per binding, including upload targets. Set `.grant_partition("host-approved-account")` only to share consent deliberately. Each target and purpose must still pass independent policy approval. Do not automatically copy event authorization to uploads.

## Prepare and complete a login

```rust,no_run
use agenthooksprotocol::{
    adapters::registered::AuthContext,
    auth::{OAuthFlow, managed::{CredentialStore, ManagedOAuth, OAuthClientConfig,
        OAuthNetwork, OAuthPolicy, OperationBudget, Preparation}},
    client::HookError,
};
use std::{sync::Arc, time::Instant};

async fn prepare_login(
    context: AuthContext,
    deadline: Instant,
    network: Arc<dyn OAuthNetwork>,
    policy: Arc<dyn OAuthPolicy>,
    store: Arc<dyn CredentialStore>,
) -> Result<(ManagedOAuth, Preparation), HookError> {
    let config = OAuthClientConfig::new(
        "account-a", "registered-client", OAuthFlow::AuthorizationCodePkce,
    )
    .redirect_uri("https://app.example/oauth/callback")
    .scopes(vec!["hooks".into()], vec!["hooks".into()]);
    let oauth = ManagedOAuth::new(config, network, policy, store)?;
    let prepared = oauth.prepare(context, OperationBudget::until(deadline)).await?;
    Ok((oauth, prepared))
}
```

For `Preparation::Ready`, use the credential only for its approved target. For `InteractionRequired`, display `pending.authorization_url()`, receive the callback at `pending.redirect_uri()` through host-owned transport and call `complete(context, callback, budget)`; the login is found by the callback's `state`. As in MCP clients, a pending login belongs to the `ManagedOAuth` that created it. With `.persist_pending_logins()` it is stored in the grant record instead, so any process sharing the store can complete it, for example from a pasted callback URL. Do not log either URL. Keep the `PendingLogin` handle to call `cancel_login`. Dropping a future cancels its work; it does not spawn a detached exchange.

Only host `prepare` creates a pending login. Delivery, challenge handling and the unbound up-front lookup return `interaction_required` instead. A pending login's lifetime is fixed at creation by `.login_lifetime(...)` (default and maximum 10 minutes), independent of the creating call's budget; expired logins are deleted, including by any host `prepare` for that grant. Each `prepare` that needs consent creates a new login with its own redirect, client, PKCE verifier and ceiling. Up to `.max_pending_logins(n)` (default 5) may be pending per grant key; creating one beyond that cancels the oldest, atomically under the grant lock when persisted. Completing one leaves the others valid, and each completion replaces the grant's client and tokens, so the newest completed login wins; a concurrent step-up may lose scopes the other added until another `insufficient_scope` challenge. A pending login records the required set it was prepared with; `complete` succeeds only if the grant within the current ceiling covers it, else it fails `access_denied` carrying that set, with the grant saved and the login consumed. Every `complete` error reports `HookError::login_ended()`: true when the login named by the callback's `state` no longer exists (consumed, expired or unknown), false when it is still pending, such as after a stray callback rejected before the claim. A pending login ends exactly once: completion (including consent denial), `cancel_login` (including by the cap) or expiry. `complete` first finds the login the callback's `state` names: with no, an unknown, an expired or an ended `state` it fails `interaction_required`. It then validates the callback (exact redirect, issuer, no fragment or userinfo, exactly one non-empty `code` or `error`, no duplicated parameter); an invalid callback fails `access_denied` and never consumes the login. A valid callback is claimed once before the code exchange; after that, a token-endpoint `invalid_grant` fails `interaction_required`, `invalid_client` fails `credential_unavailable` for a pre-registered client, `invalid_configuration` for a CIMD client and `interaction_required` for a DCR client, and other token-endpoint failures or invalid token responses fail `provider_failed`. A failed initial exchange persists nothing. Canceling never deletes a valid grant.

Redirects must use HTTPS, HTTP to a literal loopback IP (`127.0.0.0/8` or `::1`), or an RFC 8252 reverse-domain private-use scheme such as `com.example.app:/callback`. HTTP DNS names, including `localhost`, and remote HTTP redirects are `invalid_configuration`, checked before client selection or any request. `.redirect_uri(...)` sets a default. A host that binds a new loopback port per login, as MCP clients do, passes each one with `prepare_with(context, PrepareOptions::new().redirect_uri("http://127.0.0.1:<port>/callback"), budget)`; the authorization, registration and token requests and the callback check use that exact redirect, including its port. No implicit listener is installed.

## Use configured or discovered endpoints

An explicit OAuth binding fixes issuer, resource, client and flow. It skips protected-resource metadata discovery, but still validates issuer metadata and local constraints. Unbound endpoints use RFC 9728 protected-resource discovery, with strict retrieval-source/resource identity and local approval before credentials are issued. Resource identifiers retain exact trailing slash and query identity; they are not normalized into a different configured identifier.

Once a validated, locally approved binding is stored for a destination, its token is sent on the first attempt, including for notifications and uploads that are never replayed, and after recreating a provider with the same store. That lookup never creates a login and never runs protected-resource discovery. It refreshes an expired token, or re-acquires a client-credentials grant, with the authorization-server metadata persisted on the binding; if that metadata is absent it fetches only the stored issuer's metadata (`discovery_failed` on failure). A known binding that cannot be renewed fails the operation, for example `interaction_required` when PKCE needs consent. Only a store miss or a host policy refusal sends anonymously. If a renewal fails where the token endpoint provably did not process it (a DNS, TCP connect or TLS handshake failure that `OAuthNetwork::send` marks with `HookError::request_not_sent`, or a 404/410), the stored issuer's metadata is refetched once and the renewal retried once. Ambiguous failures after sending (timeouts, resets, 5xx, non-OAuth bodies, redirects) return `provider_failed` with no immediate retry, so a rotated refresh token is never replayed; a changed issuer or failed refetch is `discovery_failed`. Challenge handling, and a `prepare` that needs an exchange or login, always run full protected-resource discovery (honouring a challenge's `resource_metadata`), so a resource moved to another authorization server is rebound even while the old one still answers; `prepare` also rebinds when policy no longer approves the stored issuer. A known binding for a different client or flow is `discovery_failed` at lookup. A host `prepare` serves a usable cached token without metadata calls; when an exchange or login is needed it re-runs discovery, which repairs stale binding metadata. A 401 or `insufficient_scope` on a notification or upload is not replayed, but challenge handling (discovery, client-credentials acquisition) prepares the next attempt. Hosts can prepare an unknown target before its first call. Mutable capabilities and client-secret rotation do not invalidate a compatible grant.

PKCE uses S256, state and redirect validation, and advertised issuer-response checks. Every token exchange and refresh includes RFC 8707 `resource`.

## Register a client

The SDK takes a binding's `client_id` from exactly one source, per exact issuer and flow, in this order:

1. **Pre-registered**: the client of `OAuthClientConfig::new(namespace, client_id, flow)`, or an explicit preset's `clientId`. CIMD and DCR are then never attempted.
2. **Client ID Metadata Document**: with `OAuthClientConfig::unregistered(namespace, flow)` and `.client_id_metadata_document(url, redirect_uris)`, for PKCE only, when issuer metadata has `client_id_metadata_document_supported` equal to JSON `true`. The URL is the `client_id` verbatim and must be `https` with a path and no userinfo, fragment or dot segments; each login's redirect must be one of the document's `redirect_uris`, where a loopback `http` redirect is compared without its port (RFC 8252 section 7.3), so the document may declare `http://127.0.0.1/callback`. Otherwise `invalid_configuration`, before any login is created. The SDK never fetches the URL. The client is public (`none`); an `invalid_client` for it, on the authorization callback or at the token endpoint, is `invalid_configuration`, never a DCR fallback.
3. **Dynamic Client Registration** (RFC 7591): only with `.dynamic_registration(RegistrationPolicy::new(issuer, client_name))` for that exact issuer and an advertised HTTPS `registration_endpoint` that passes `OAuthNetwork::check` with `EndpointUse::Registration` (else `untrusted_destination`; redirects are never followed). The policy also supplies optional `software_id`, `software_version`, a registration `scope` and an `initial_access_token(reference, token)`, which is sent as a Bearer credential only to that issuer's registration endpoint and never persisted. Client credentials also need `.client_secret_storage(...)` and a `client_secret_basic` or `client_secret_post` token-endpoint method.
4. Otherwise `credential_unavailable`.

A recorded selection survives authorization-server metadata changes and is replaced only when host policy changes it. A different client identity is a different grant: old tokens are never presented under the new client. PKCE then needs consent; client credentials re-acquire.

As in MCP clients, a PKCE client is registered inside each `prepare` that creates a login, with that login's exact redirect and `application_type: "native"` for a loopback redirect; delivery paths never register and return `interaction_required`. The login holds the issued `client_id` (any `client_secret` in the response is ignored), and completion stores it with the tokens in the grant record, which refresh then uses. There is no PKCE registration record. An `invalid_client` at completion ends only that login and returns `interaction_required`; at refresh it returns `interaction_required` and deletes the grant only while the stored record still holds the presented client and refresh token. `registration_access_token` and `registration_client_uri` are ignored.

Client credentials keep one registration record per namespace and exact issuer in the same `CredentialStore`, reused by every client-credentials grant there. `prepare` and non-interactive acquisition, including the up-front lookup and challenge handling, register under that key's lock when no usable record exists, so concurrent processes register once. Like a token exchange, a registration request carries `RequestWritten`: once marked, its response is received and committed (secret stored, record written) even if the caller is dropped; before that, cancellation aborts it. Issued client secrets go only through `ClientSecretStorage` (store, resolve, delete by an SDK-chosen reference); records hold the reference, and replaced or deleted registrations have their secret deleted. A record is unusable when its secret expired or cannot be resolved. A usable record is replaced only by `prepare_with(context, PrepareOptions::new().force_registration(), budget)`, for example after changing the `RegistrationPolicy`; a failed forced replacement returns its error, keeps the current record and counts toward the backoff. An `invalid_client` token response deletes that registration; the SDK registers and re-acquires once more, and a repeated `invalid_client` is `credential_unavailable` and counts as a failed registration. After a failed registration no registration request is sent until a backoff passes (`.registration_backoff(initial, max)`, default 1 minute doubling to 1 hour, or a later `Retry-After`, in delta-seconds or HTTP-date form, up to `max`), shared through the store; meanwhile operations that need a registration return the last failure's code, so a transient failure stays `provider_failed`. A host `prepare` bypasses the backoff. The failure count survives the re-registration after an `invalid_client`, so a server that keeps rejecting new clients is retried less often, and resets once a token request with the registered client succeeds. A still-valid stored token keeps working meanwhile.

Delivery diagnostics (`DeliveryDiagnostic`) and observation failures carry the typed `auth_code` and validated `required_scopes`, so a host can tell `interaction_required` (run login for that backend) from a transport failure.

## Use client credentials

Choose `OAuthFlow::ClientCredentials` and, for a pre-registered client, `.client_secret(reference, secret, TokenAuthMethod::ClientSecretBasic)` or explicitly supported `ClientSecretPost`. Construct the SDK-owned `ClientSecret::new(...)` from a host-resolved secret; never put its value in protocol configuration. The type has no `Debug` or serialization implementation; explicit secret access and serialized session records still require care. Secret memory is not automatically zeroized. The explicit target's client ID and optional secret reference must match. Issuer metadata must support the flow and token-auth method. Client credentials reacquire noninteractively and never request human login.

## Recover and replay

Known-expiry tokens refresh with a 30-second margin. Tokens without `expires_in` remain usable until rejected. `expires_in` must be a positive integer or a string of ASCII digits; other values, including `null`, fail `provider_failed`. Token requests carry a `RequestWritten` extension; `OAuthNetwork::send` must call its `mark()` once the request bytes are written; clients like reqwest that cannot observe write completion should mark once the connection is established, or when the send future is first polled after connecting, as an approximation. From then on the grant lock is held until the outcome is committed, so a concurrent caller waits (bounded by its own deadline) instead of re-presenting a spent refresh token. Before that (DNS, connect, TLS), caller cancellation aborts the request and releases the grant lock. Each token exchange runs on a spawned Tokio task that owns the grant guard. Once the request is written, that task receives the response and commits the whole outcome itself (including a rotated refresh token from an undecodable JSON or form-encoded 2xx) under a fresh `.commit_timeout(...)` budget (default 30 seconds), and only then reports to the caller. A slow store, an expired caller deadline or a dropped future therefore never leaves a spent refresh token stored as current. A 401 rejection is persisted before any discovery or renewal; if challenge discovery fails transiently, renewal proceeds through the still-valid cached binding. A failed refresh response clears in-flight state and keeps a valid rotated refresh token, otherwise the presented one. Timeouts, non-OAuth responses and 5xx keep refresh material and return `provider_failed` (retry); the next acquisition retries the refresh token by default. A definitive refresh `invalid_grant` returns `refresh_rejected` and drops both tokens only if the store still holds the presented refresh token.

A 401 marks the rejected token stale before any other decision, even when its expiry is unknown or in the future. As in MCP clients, a 401 challenge's `scope` (within the ceiling) is added to the scopes requested by the next acquisition or sign-in; it is never a requirement and never causes `access_denied`; challenge handling renews it by refresh or client-credentials re-acquisition and never resends it, including after a notification or upload that is not replayed. A delayed rejection of an older token generation cannot invalidate a newer token. `auth_code()` and `auth_recovery()` provide sanitized classifications (`configure`, `login`, `retry` or `none`).

A Bearer 403 with `error="insufficient_scope"` requires its scopes for that operation only; they are never stored. Without a `scope`, the host-required scopes are used, or it fails `access_denied` with no scopes. If the stored grant already records the required set as granted, it fails `access_denied` carrying it: the token is not replayed and no login is created. Other 403 responses are denied. A malformed challenge (an empty `scope`, repeated, leading or trailing spaces, an invalid character or a duplicated parameter) fails `access_denied` with no scopes, and a 403 whose challenge cannot be parsed is not retried. Client credentials can acquire the broader grant. PKCE fails `interaction_required` carrying `HookError::required_scopes()`; pass them to `prepare_with_required` to request step-up consent. Required scopes outside the ceiling fail `access_denied`.

After the provider handles a 401 or `insufficient_scope` challenge, the HTTP transport replays `hooks/intercept`, `hooks/configuration` and `hooks/capabilities` once, with the same JSON-RPC id and buffered body. A second rejection is an operational failure. Notifications and uploads are never replayed; uploads still run challenge handling for a 401 or Bearer 403 `insufficient_scope` and report the provider's classified error.
